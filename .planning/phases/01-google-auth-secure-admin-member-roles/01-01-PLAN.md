<threat_model>
## Threat Model

### Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Browser client | Untrusted user-controlled UI and requests | Session cookie, route requests, upload/download actions |
| Google OAuth provider | Identity source only | Authorization code, ID token, profile claims |
| Next.js server routes | Enforcement boundary | Auth state, role decisions, signed download URLs |
| Storage backend | Must not be directly exposed to the client | Signed object access, upload completion, delete operations |

### Threats and Controls

| Threat | Risk | Control |
|--------|------|---------|
| Forged role claims | Privilege escalation if client-provided role is trusted | Resolve roles on the server from `ADMIN_EMAILS`; never trust client role state |
| Session theft | Stolen cookie grants access | Use `httpOnly`, `secure`, `sameSite` cookies and server-side session verification |
| IDOR on video records | Unauthorized viewing, deletion, or download | Require per-route permission checks for every video action |
| Storage URL leakage | Direct object URLs bypass authorization | Return signed or time-limited URLs only after authorization checks |
| Brute-force / abuse | Excessive auth attempts or scraping | Apply per-route rate limiting and respond with `429` |
| UI-only authorization | Hidden controls still callable from the browser | Enforce 401/403 on server even when the UI hides actions |

### Security Decisions

- Google is the only sign-in provider in this phase.
- `ADMIN` is assigned from a server-side allowlist; `MEMBER` is the default authenticated role.
- Permission checks are centralized and reused by API routes and the UI.
- Mutating routes and download endpoints are protected by the same authorization layer.
</threat_model>
